# Resume onboarding

Return through the approved support and sharing procedure for your actual
plan and tool version. Keep your own saved work and ask the onboarding owner
when instructions disagree. Do not replace newer preparation or personal work
with an older invitation just to get back to a familiar screen.

To recover an interrupted invitation opening, use its reported transaction token
with the same selected record root and state home:

```text
onboard-kit start --resume-import TOKEN --root DIR [--home DIR]
```

Recovery does not need the original ZIP. Review the displayed pending actions
before choosing resume. A completed opening awaiting cleanup instead offers
clean; cleanup preserves later owner edits and may finish without displaying a
session when its staged display is gone. Cancel retains recovery state. Keep
recovery data until the tool confirms cleanup; do not guess another destination
or delete unknown files to force progress. Ask the owner when context or stored
work has changed. A reported token is a selector, not proof of valid recovery.

The token applies only to interrupted opening or its cleanup. It is not a
general command for returning to completed onboarding. The invitation route
opens a read-only record-backed session: existing answers, outcomes and waiting
work can be displayed, but answers and outcomes cannot be edited there and
commands or checks are not executed. Only confirmed begin for a genuinely new
local record records firstOpenedAt; existing events stay unchanged and an
existing missing event stays unknown. Recovery uses its frozen event rather
than sampling first use again.

The separate start --org-plan route remains the legacy organization-plan flow.
The existing walk command is a legacy plan-file question walkthrough: accepted
answers are saved in that selected plan file. Neither route silently becomes
record-backed answer or outcome editing.

For a completed invitation session, use its registered session key and explicit
absolute record root and state home:

```text
onboard-kit session edit --root ABS --home ABS --session KEY
```

Confirm the displayed account exactly, including its double quotes. Choose one
answer, follow-plan choice or outcome, review the complete proposed effect, then
choose save or cancel. Only the selected record changes; the plan, preparation,
registration, first-use event and historical reference stay intact. Follow-plan
removes one personal override and may reveal an existing shared answer. Defaults
remain suggestions. Outcome verification still requires an explicit statement;
the tool does not run checks. Pending imports and changed source files refuse
rather than bypassing review. Ask the onboarding owner if the registered context
is unknown; do not guess a key or move state to force acceptance.

In the activity model, verified means the required capability or result was
actually established; failed means an attempted result did not work; deferred
means intentionally postponed. A request sent, an onboarder arrangement or a
date passing is none of those verified outcomes. A displayed instruction or
read-only session does not record that an activity was completed.

Report blockers, incorrect instructions, missing files, a wrong account or an
unsupported plan version without sharing credentials or complete private records.
Reading this help or rendering a preview records no first use or employment
start date, accepts no unanswered default and completes no activity.
